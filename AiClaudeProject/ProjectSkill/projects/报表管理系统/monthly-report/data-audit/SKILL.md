# 技术支持月报 - 数据审计核实确认

## Overview

本 skill 负责对已获取的月报原始数据进行统计分析、质量审计和核实确认。所有数据验证通过后，才可进入最终报告输出阶段（参见 `tech-support-monthly-report-output`）。

月报相比周报，增加了以下审计维度：
- 按周汇总的月度趋势数据（工单、用户量、咨询量、故障）
- 问题类型分布统计（饼图数据）
- 高频问题根因归类（根因类型占比）
- 已解决/未解决问题的状态核实
- 工作总结与下月计划的合理性检查

---

## 一、关键指标与数据规则

### 1.1 关键指标说明

- **客满工单**: 客户提交的总工单量
- **技术工单**: 技术支持需要处理的工单
- **技术支持解决率**: 技术支持独立解决的工单占比。达标标准：≥ 85%。
- **两小时工单完成率**: 2小时内完成处理的工单占比。达标标准：≥ 95% 为达标，< 95% 为不达标。显示值和达标判断均四舍五入取整（如 83.33% → 83%，94.44% → 94%）。
- **P1/P2故障**: 重大/紧急线上故障。目标值：0。
- **P3/P4故障**: 一般/轻微线上故障。
- **月活跃用户（UV）**: 当月独立访问用户数，单位为万。
- **月咨询量**: 当月用户咨询总量。

### 1.2 数据来源优先级

月报中的各工单量数据（如"核心摘要"、"业务组月度指标汇总"表格中的工单相关指标）应首先参照"业务指标详情"中的数据进行填充。原始报表文档中的"技术支持工单明细.xlsx"中的工单摘要数据仅用于工单问题分析、TOP问题分析、高频问题分析等定性分析场景，不得用于统计工单量并填充到其他工单数据字段中。

### 1.3 两小时工单完结率规则

**达标标准**：两小时工单完结率 ≥ 95% 为达标，< 95% 为不达标。

**四舍五入取整规则**：若两小时工单完结率含有小数点（如 83.33%、94.44%），需先四舍五入取整（83.33% → 83%，94.44% → 94%），再以取整后的值与 95% 阈值比较判断达标/不达标。核心摘要和各表格中显示的值也使用取整后的值。

**取数规则**：核心摘要中的"2小时工单完成率"取各业务组对应指标，**排除含"外部"和"累计"的指标**：
- 数智财务组：取"技术支持两小时工单完成率（内部）"
- 免疫规划组：取"技术支持两小时工单完成率"
- 数字支撑组：取"技术支持两小时工单完成率"
- 电子档案组：取"技术支持两小时工单完成率（内部）"

### 1.4 环比变化率计算规则

环比变化 = 本月值 - 上月值。正数标注 `▲`（上升），负数标注 `▼`（下降），0 标注 `—`（持平）。

**变化率计算公式**：
- 如果本期 ≥ 上期：`(本期 - 上期) / 上期 × 100%`
- 如果本期 < 上期：`(上期 - 本期) / 上期 × 100%`

### 1.5 达标判断规则

| 指标 | 达标条件 | 不达标条件 |
|------|---------|-----------|
| 技术支持解决率 | ≥ 85% | < 85% |
| 2小时工单完成率 | ≥ 95%（取整后） | < 95%（取整后） |
| P1/P2故障数 | = 0 | > 0 |

### 1.6 需求数据统计规则

需求链接数据统计的是**当前所有未完成的需求**（即状态不是"已完成"的需求），而非仅统计本月新创建的需求。目的在于展示当前各业务组仍在进行中的需求全景。

### 1.7 超期工单取数规则

超期工单数据直接从 `AiClaudeProject/原始报表文档/技术支持工单明细.xlsx` 获取，根据表格中的"是否超时"字段判断（值为"是"即为超期工单），按"二级部门"或"模块"归类到对应业务组的超期工单表格中。

**特殊规则**：附录1（数智财务组 + 电子档案组）中所有模块的超期工单，需**排除超期原因为"外部超时"的工单**，仅保留其他超期原因（如开发超时、运营超时等）的工单。其他业务组（免疫规划组、数字化支撑组）的超期工单不在此排除规则内，全部超期工单均需记录。

### 1.8 非客满统计取数规则

**数据来源**: Confluence 页面"翡翠月报数据看板" (pageId: 278883515)

**取数规则**: 在"翡翠月报数据看板"表格中，按"统计月"列匹配目标报告月（如 2026-06），从对应行中提取以下字段：

| 看板列名 | 月报字段 | 所属附录 |
|---------|---------|---------|
| 浙里报机器人转人工申请量 | 自助转技术支持工单 | 附录1 非客满统计 |
| 浙里报PM技术工单量 | 运营提交技术工单 | 附录1 非客满统计 |
| 疫苗PM技术工单量 | PM提交技术工单量 | 附录2 工单详情 |

**禁止行为**:
- 禁止从 Excel 工单明细中推算非客满统计数据
- 禁止模型自行估算或猜测非客满统计数值
- 若 Confluence 页面不可达或 token 失效，填写"—"，标注"待从 Confluence 获取"

### 1.9 已解决TOP问题判断标准

"本月已解决TOP问题"仅列入**本月内通过代码修复或配置变更彻底解决**的问题。以下情况**不计入**：
- 临时 workaround（如手动订正数据、引导用户绕过问题）
- 问题根因未消除，仅处理了表面症状
- 上月已修复、本月仅验证确认的问题

## 二、按周汇总趋势数据审计

### 2.1 周划分规则

将自然月按日历周划分为 4-5 周：
- 第1周：1日-7日
- 第2周：8日-14日
- 第3周：15日-21日
- 第4周：22日-28日
- 第5周：29日-月末（如有）

### 2.2 按周汇总工单数据

```python
from collections import defaultdict
import datetime

# 按周汇总
weekly_tickets = defaultdict(list)
for t in month_tickets:
    day = t['date'].day
    if day <= 7:
        week = 1
    elif day <= 14:
        week = 2
    elif day <= 21:
        week = 3
    elif day <= 28:
        week = 4
    else:
        week = 5
    weekly_tickets[week].append(t)

# 每周统计
for w in range(1, 6):
    tickets = weekly_tickets[w]
    customer_count = len(tickets)
    tech_count = len([t for t in tickets if t['category'] != '客满咨询类-基础咨询'])
    solved_count = len([t for t in tickets if '已解决' in t.get('desc', '')])
    print(f"第{w}周: 客满{customer_count} 技术{tech_count} 解决{solved_count}")
```

### 2.3 按周汇总用户量和咨询量

从业务指标详情或 Confluence 看板中获取各业务组按周的用户量和咨询量数据，填入趋势图表格。

**审计要点**：
- 各周数据之和应等于月度汇总数据
- UV 数据单位为"万"
- 若某周数据缺失，标注"—"，并在趋势分析中说明

### 2.4 按周汇总故障数据

从 Confluence 或故障管理系统获取按周的故障数据，注意区分：
- P1/P2（累计）：月度累计值
- P3/P4（累计）：月度累计值
- 外部故障（累计）：月度累计值
- 故障总数（新增）：每周新增故障数

## 三、问题类型分布审计

### 3.1 问题类型分类标准

从工单摘要中按以下标准归类问题类型：

| 问题类型 | 归类关键词/规则 |
|----------|---------------|
| 功能咨询/使用指导 | 咨询、怎么用、如何操作、在哪里、功能说明 |
| 系统故障/异常报错 | 报错、异常、崩溃、无法访问、白屏、500、404 |
| 数据问题/订正 | 数据不对、数据缺失、订正、同步失败、数据不一致 |
| 需求/优化建议 | 建议、希望、能不能、优化、新增功能 |
| 权限/账号问题 | 权限、登录不了、账号、密码、无权访问 |
| 配置/环境问题 | 配置、环境、部署、参数、设置 |
| 其他 | 无法归入以上类型的工单 |

### 3.2 统计方法

```python
type_keywords = {
    "功能咨询/使用指导": ["咨询", "怎么用", "如何操作", "在哪里", "功能说明", "指导"],
    "系统故障/异常报错": ["报错", "异常", "崩溃", "无法访问", "白屏", "500", "404", "超时"],
    "数据问题/订正": ["数据不对", "数据缺失", "订正", "同步失败", "数据不一致", "数据错误"],
    "需求/优化建议": ["建议", "希望", "能不能", "优化", "新增功能"],
    "权限/账号问题": ["权限", "登录不了", "账号", "密码", "无权访问"],
    "配置/环境问题": ["配置", "环境", "部署", "参数", "设置"],
}

type_counts = Counter()
for t in month_tickets:
    desc = t['desc']
    matched = False
    for type_name, keywords in type_keywords.items():
        if any(kw in desc for kw in keywords):
            type_counts[type_name] += 1
            matched = True
            break
    if not matched:
        type_counts["其他"] += 1
```

**审计要点**：
- 各类型占比之和应为 100%
- 类型分布应与上月对比，标注异常变化

## 四、高频问题根因归类审计

### 4.1 根因类型分类标准

| 根因类型 | 说明 |
|----------|------|
| 系统Bug/代码缺陷 | 代码逻辑错误、边界条件未处理、回归问题 |
| 数据同步/一致性问题 | 系统间数据同步延迟、不一致、丢失 |
| 用户操作/认知问题 | 用户误操作、不熟悉系统功能、培训不足 |
| 配置/部署问题 | 配置错误、部署遗漏、环境差异 |
| 第三方依赖问题 | 外部系统故障、接口异常、第三方服务不可用 |
| 需求缺失/设计缺陷 | 功能设计不完善、需求遗漏、交互不合理 |

### 4.2 归类方法

对每条高频问题，从工单摘要和处理备注中提取根因，归入对应的根因类型。同一高频问题可能涉及多个根因，取主要根因。

### 4.3 审计要点

- 根因归类占比之和应为 100%
- 重点关注"系统Bug/代码缺陷"和"数据同步/一致性问题"两类，通常占比最高
- 如"用户操作/认知问题"占比异常高，说明产品易用性存在问题

## 五、高频问题详情审计

（同周报 data-audit 的第四部分，略）

对 TOP 3-5 高频问题，逐一展开详情。要求输出内容**精炼准确**，让读者快速理解问题本质和原因。

### 5.1 选取高频问题

取 `issue_counts.most_common(5)` 中数量 > 1 的问题类型，按工单量从高到低排序。

### 5.2 问题归类与拆分规则

- **归类（聚类）**：症状相同、根因相同、处理方式相同的工单 → 归入同一条
- **拆分（新问题）**：症状不同、根因不同的新问题 → 单独另起一条
- **上限约束**：同一高频问题下的症状变体不超过 5 个

### 5.3 问题描述编写规范

```
【格式】用户场景 + 操作路径 + 遇到的错误/异常现象 + 影响范围
```

要求：
- 选取 2-3 个典型症状描述，归纳核心问题模式
- 不需要列出具体单位名称
- 篇幅控制在 3-5 句话

### 5.4 月报特有的高频问题输出格式

月报高频问题表格需要包含**长期改进措施**列，体现月报的总结性：

| 序号 | 问题分类 | 问题描述 | 出现频次 | 影响业务 | 根本原因 | 临时解决方案 | 长期改进措施 |
|:---:|:---|:---|:---:|:---|:---|:---|:---|

**长期改进措施**编写要求：
- 从根因出发，提出可落地的改进方案
- 涉及代码修复的，说明修复方向（如"增加支付状态同步重试机制"）
- 涉及流程的，说明流程优化点（如"建立发票推送监控告警"）
- 不可写"加强监控"、"提升质量"等空泛内容

## 六、已解决问题核实

### 6.1 核实标准

对每条标记为"已解决"的问题，核实：
- 解决日期是否在本月内
- 解决方案是否具体可验证（非"已处理"、"已修复"等模糊描述）
- 是否有对应的代码提交、配置变更或发布记录

### 6.2 输出格式

| 序号 | 问题描述 | 所属业务 | 问题类型 | 解决日期 | 解决方案 | 状态 |
|:---:|:---|:---|:---:|:---:|:---|:---|

## 七、工作总结与下月计划审计

### 7.1 工作亮点编写要求

- 基于本月实际数据，提炼 3 个亮点
- 亮点应可量化（如"工单解决率提升至 XX%"、"完成 X 个需求上线"）
- 不可编造不存在的数据

### 7.2 工作不足编写要求

- 基于本月实际数据，指出 2 个不足
- 不足应可量化（如"P1/P2 故障 X 个未达标"、"两小时完结率下降至 XX%"）

### 7.3 下月计划审计

- 计划应具体、可执行
- 每项计划应有明确负责人和预计完成时间
- 优先级合理（P0 > P1 > P2）

## 十、自检清单

在数据审计完成、进入输出阶段之前，确认以下各项：

- [ ] 所有两小时完结率是否已四舍五入取整，不保留小数位
- [ ] 两小时完结率达标判断是否基于取整后的值与 95% 比较
- [ ] 工单量数据是否优先从业务指标详情获取（非从工单明细 Excel 统计）
- [ ] 需求列表是否已排除"已完成"状态
- [ ] 非客满统计是否从 Confluence "翡翠月报数据看板" (pageId: 278883515) 获取，禁止自行估算
- [ ] 附录1 超期工单是否已排除"外部超时"原因
- [ ] 各业务模块归属附录是否正确
- [ ] 趋势标注（▲/▼/—）是否与环比变化一致
- [ ] TOP问题是否有明确的边界，不重复、不遗漏
- [ ] 按周汇总数据各周之和是否等于月度总计
- [ ] 问题类型分布占比之和是否为 100%
- [ ] 根因归类占比之和是否为 100%
- [ ] 已解决问题是否均在本月内完成，解决方案是否具体可验证
- [ ] 工作亮点和不足是否有数据支撑
- [ ] 下月计划是否有明确负责人和完成时间

> 审计确认通过后，进入 `tech-support-monthly-report-output` skill 生成最终报告。
