# 技术支持周报 - 数据审计核实确认

## Overview

本 skill 负责对已获取的周报原始数据进行统计分析、质量审计和核实确认。所有数据验证通过后，才可进入最终报告输出阶段（参见 `tech-support-weekly-report-output`）。

---

## 一、关键指标与数据规则

### 1.1 关键指标说明

- **客满工单**: 客户提交的总工单量
- **技术工单**: 技术支持需要处理的工单
- **技术支持解决率**: 技术支持独立解决的工单占比
- **两小时工单完成率**: 2小时内完成处理的工单占比。达标标准：≥ 95% 为达标，< 95% 为不达标。显示值和达标判断均四舍五入取整（如 83.33% → 83%，94.44% → 94%）。
- **P1/P2故障**: 重大/紧急线上故障
- **P3/P4故障**: 一般/轻微线上故障

### 1.2 数据来源优先级

周报中的各工单量数据（如"本周工单量情况"、"业务指标详情"表格中的工单相关指标）应首先参照"业务指标详情"中的数据进行填充。原始报表文档中的"技术支持工单明细.xlsx"中的工单摘要数据仅用于工单问题分析、工单TOP问题分析、高频问题分析等定性分析场景，不得用于统计工单量并填充到其他工单数据字段中。

### 1.3 两小时工单完结率规则

**达标标准**：两小时工单完结率 ≥ 95% 为达标，< 95% 为不达标。

**四舍五入取整规则**：若两小时工单完结率含有小数点（如 83.33%、94.44%），需先四舍五入取整（83.33% → 83%，94.44% → 94%），再以取整后的值与 95% 阈值比较判断达标/不达标。简述中显示的值也使用取整后的值。

**取数规则**：简述中的"本周两小时处理率"数据取自业务指标详情中各业务模块对应的以下指标，**排除含"外部"和"累计"的指标**：
- 数智财务组：取"技术支持两小时工单完成率（内部）"
- 免疫规划组：取"技术支持两小时工单完成率"
- 数字支撑组：取"技术支持两小时工单完成率"
- 电子档案组：取"技术支持两小时工单完成率（内部）"

### 1.4 需求数据统计规则

需求链接数据统计的是**当前所有未完成的需求**（即状态不是"已完成"的需求），而非仅统计本周新创建的需求。目的在于展示当前各业务组仍在进行中的需求全景。各附录中的"本周需求链接"已统一更名为"TOP需求链接"。

### 1.5 超期工单取数规则

超期工单数据直接从 `AiClaudeProject/原始报表文档/技术支持工单明细.xlsx` 获取，根据表格中的"是否超时"字段判断（值为"是"即为超期工单），按"二级部门"或"模块"归类到对应业务组的超期工单表格中。

**特殊规则**：附录1（数智财务组 + 电子档案组）中所有模块的超期工单，需**排除超期原因为"外部超时"的工单**，仅保留其他超期原因（如开发超时、运营超时等）的工单。其他业务组（免疫规划组、数字化支撑组）的超期工单不在此排除规则内，全部超期工单均需记录。

### 1.6 趋势标注规则

较上周列使用：
- `▲` 表示上升
- `▼` 表示下降
- `—` 表示持平

**变化率计算公式**：
- 如果本期 ≥ 上期：`(本期 - 上期) / 上期`
- 如果本期 < 上期：`(上期 - 本期) / 上期`

### 3.2 统计方法

```python
keywords_map = {
    "浙里报": {
        "指标同步问题": ["指标", "同步", "关联指标", "选择不到", "限额", "项目名称", "预算"],
        "支付状态异常": ["支付中", "结算中", "支付失败", "行号为空", "行号错误"],
        "发票问题": ["发票", "票据", "开具", "未显示", "被占用", "无法删除", "验真", "航班号"],
        "登录/账号问题": ["转圈", "加载中", "闪退", "浙政钉", "5分钟", "uuid"],
        "审批流问题": ["审批", "审核", "流程", "经办人看不到", "无单据"],
        "公务卡/账户问题": ["公务卡", "绑定", "银行账户", "选择不到"],
        "费用/合同问题": ["费用信息", "伙食补贴", "交通费", "工资模板", "合同金额", "政采云"],
        "平台访问问题": ["登录", "访问", "权限"],
        "数据传输问题": ["传输", "接口", "凭证"],
    },
    "数字化": {
        "账单/冲正问题": ["账单", "冲正", "冲红", "服务费"],
        "平台访问问题": ["登录", "访问", "权限"],
    },
    "电子档案": {
        "档案查询问题": ["档案", "查询", "查不到", "搜索"],
        "档案同步问题": ["同步", "归档", "上传"],
    },
    "疫苗": {
        "接种记录问题": ["接种", "记录", "查询不到"],
        "预约问题": ["预约", "取消", "时间段"],
        "数据问题": ["数据", "报表", "统计"],
        "平台访问问题": ["登录", "访问", "权限"],
    },
}

issue_counts = Counter()
issue_tickets = defaultdict(list)  # 记录每个问题类型对应的工单，用于后续详情分析
for t in week_tickets:
    desc = t['desc']
    module = t['module']
    dept2 = t['dept2']
    matched = False
    for biz, biz_keywords in keywords_map.items():
        if biz in module or biz in dept2:
            for issue_type, keywords in biz_keywords.items():
                if any(kw in desc for kw in keywords):
                    issue_counts[f"{biz}-{issue_type}"] += 1
                    issue_tickets[f"{biz}-{issue_type}"].append(t)
                    matched = True
                    break
        if matched:
            break
    if not matched:
        issue_counts[f"{module}-其他"] += 1
        issue_tickets[f"{module}-其他"].append(t)
```

**输出格式**:

```
| 问题描述 | 所属业务 | 数量 | 占比 |
|----------|---------|------|------|
| 指标同步问题 | 浙里报 | X | X% |
| 支付状态异常 | 浙里报 | X | X% |
| 发票问题 | 票据管理 | X | X% |
| ... | ... | ... | ... |
```

## 四、高频问题详情

对 TOP 3-5 高频问题，逐一展开详情。要求输出内容**详细且准确**，不可泛泛而谈。

### 4.1 选取高频问题

取 `issue_counts.most_common(5)` 中数量 > 1 的问题类型，按工单量从高到低排序。

### 4.2 问题归类与拆分规则

从每个问题类型对应的工单列表中，通读所有工单摘要，做以下判断：

- **归类（聚类）**：症状相同、根因相同、处理方式相同的工单 → 归入同一条高频问题分析，工单数量合并统计
- **拆分（新问题）**：同一模块下出现的症状不同、根因不同的新问题 → 单独另起一条分析，不可混入已有的高频问题中。即使数量只有 1-2 条，只要问题性质独立，也应单独列出
- **判断标准**：两条工单是否可以归到一起，看它们的"用户遇到了什么问题"和"为什么会发生"是否一致，而非只看关键词是否匹配

### 4.3 问题描述编写规范

问题描述是分析的核心，必须让读者**无需查看原始工单即可理解问题全貌**。编写时遵循以下结构：

```
【格式】用户场景 + 操作路径 + 遇到的错误/异常现象 + 影响范围

【反例】"发票问题"、"支付状态异常" — 只有症状标签，无法理解
【正例】"用户在浙里报提交差旅报销单时，关联的机票发票状态显示'同程未推送'，
       点击刷新按钮无响应，行程结束已超过3个工作日，导致用户无法完成报销提交"
```

要求：
- 每个问题描述不少于 2 句话，完整描述用户场景和问题表现
- 列举 3 个以上具体症状变体（如同类问题下的不同表现）
- 标注该问题涉及的工单数量

### 4.4 原因归纳

从工单的处理备注中提取根因，将相同根因的工单归并，形成统一的根因描述。需包含：
- 涉及的系统/服务（如一体化、数新、同程、浙政钉、国家平台等）
- 触发条件（什么情况下会出现这个问题）
- 影响范围（影响了哪些用户/场景）

### 4.5 处理方式归纳

从工单的处理备注中提取实际执行的处理动作，归纳为标准化的处理方式描述。需说明具体谁来做了什么操作（如"后台手动触发同步"、"引导用户联系同程客服重开"）。

### 4.6 输出格式

每条高频问题按照以下格式输出，标题中标注工单数量：

```
【{业务模块}-重点高频问题{N}】（{X}条）
问题描述：{详细描述，包含用户场景、操作路径、错误现象，至少2句话}
处理方式：{具体处理动作，说明谁做了什么}

问题原因：{根因描述，包含涉及的系统/团队、触发条件、影响范围}
```

### 4.7 分析示例（参照以下质量标准）

```
【浙里报-重点高频问题1】（14条）
问题描述：用户报销时发现支付限额未同步到浙里报，导致报销单关联不到预算指标；
部分用户银行回单在财务管理中同步N次仍无数据，2025年7月以来的回单和电子凭证
均缺失；另有报销单流程走完、实际已支付，但浙里报状态仍显示"结算中"而非"支付
成功"；还有项目名称已在一体化维护但浙里报未同步，用户需手动联系技术支持同步。
处理方式：后台手动触发同步支付限额和项目名称；引导用户联系一体化系统排查支付
结果回传问题；排查核算云归档状态，撤回重新挂靠银行回单；联系数新同步拉取缺失数据。

问题原因：一体化系统与浙里报之间的数据同步链路存在延迟或推送失败，支付限额终
审后未自动同步到浙里报；银行回单在凭证移交后无法挂靠；一体化支付结果回调浙里
报失败导致状态不一致；部分预算指标缺少支出场景配置导致报销单无法关联。
```

### 4.8 提取处理方式的技巧

从工单摘要中提取处理结果时，注意以下模式：

| 工单摘要中的原文 | 提取的处理方式 |
|-----------------|---------------|
| `,。已处理 让用户再操作传输下` | 手动触发重新传输 |
| `,1,现在是有发票的，后续先让用户点击查看刷新` | 引导用户刷新查看 |
| `,让用户刷新页面再试下` | 缓存问题，刷新解决 |
| `,联系数新处理同步` | 联系数新同步拉取 |
| `,已排查，核实为一体化未同步` | 排查核实和联系一体化处理 |
| `,引导用户升级浙政钉版本` | 引导用户升级浙政钉版本 |
| `,修改配置，重跑数据` | 修改配置，重跑数据 |
| `,咨询排查和数据订正` | 咨询排查和数据订正 |
