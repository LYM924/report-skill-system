## 二、今天遇到的问题与优化

### 问题 1：公司映射后的模型在配置中心"连不上"

**现象**：公司内部 App 系统提供的 Claude Code 配置（ANTHROPIC_BASE_URL=公司网关、模型映射 glm-5.1 / glm-4.5-air、平台申领的 AppKey）无法在知识库配置中心正常使用。

**排查过程**：
1. 用 curl 实测网关：SDK 标准路径（base_url + `/v1/messages`）+ `Authorization: Bearer` → HTTP 200，glm-5.1 / glm-4.5-air 非流式、流式均正常；
2. 用项目锁定的 `anthropic==0.34.0` 复现应用调用路径 → 构造客户端直接报 `TypeError: __init__() got an unexpected keyword argument 'proxies'`；
3. 检查 requirements.txt → 发现两处问题（见根因 1、2）。

**根因与优化**：

| # | 根因 | 优化 |
|---|------|------|
| 1 | `anthropic==0.34.0` 依赖 httpx 未钉版本；httpx≥0.28 移除了 `proxies` 参数，SDK 构造客户端即抛 TypeError，**所有 Anthropic 协议调用全挂** | requirements.txt 钉 `httpx==0.27.2`（已验证与 anthropic 0.34.0 / openai 2.x 兼容） |
| 2 | requirements.txt 第 22 行 `sentence-transformers>=2.2.0openai>=1.40.0` 两行依赖被拼成一行，`pip install -r` 解析失败（Docker 构建会报错） | 拆分为两行 |
| 3 | 配置中心没有公司网关预设；若误选「智谱 GLM」预设（公网 bigmodel.cn + OpenAI 协议），公司 AppKey 必然鉴权失败 | 新增预设 `cai-gateway`「公司AI网关（GLM映射）」：协议 anthropic、网关地址内置、推荐模型 glm-5.1 / glm-4.5-air；原有 9 家预设未动 |

**关键实测结论**：公司网关**仅接受 `Authorization: Bearer` 鉴权**，不接受 `x-api-key`（返回 "Request denied by Key Auth check. No API key found in request"）；且网关对任意模型名都能路由（按平台映射）。应用代码本身 Bearer 优先，无需改动。

### 问题 2：配置中心「测试连接」报 "Request denied by Key Auth check. No API key found in request"

**现象**：用户按正确方式配置后点测试连接，报上述鉴权错误。

**排查过程**：
1. 直接调现网测试接口：传完整 key → 成功；key 留空（用已保存的）→ 成功。说明服务端链路正常；
2. 解密数据库 `ai_configs` 表实际存储的 key → 发现存的是**脱敏垃圾值** `sk-1****c970`（12 字符）；
3. 定位代码：前端 `loadConfig` 把后端返回的脱敏 key（`api_key_masked`）回填进 AppKey 输入框，测试/保存时原样提交；用户某次点「保存配置」时把脱敏值存进了数据库，此后无论怎么测都鉴权失败。

**优化**：
- 前端：AppKey 含 `****` 视为"未修改"——测试连接自动用已保存的密钥，保存时保留原密钥（堵住回填陷阱）；
- 后端：`test_ai_config` 仅在 `AuthenticationError` 时回退 x-api-key，不再用"找不到 API Key"掩盖模型/网络等真实错误；
- 数据修复：将 admin 账号库中垃圾 key 换回真实 AppKey，配置改为 provider=cai-gateway + model=glm-5.1；
- 已核查 `ai_configs` 全表：仅 admin 一行，已修复，无其他用户受损数据。

## 五、待办 / 遗留事项

### 高优先级

1. **本地运行环境与 Docker 依赖分叉**：本机实际运行的是 anthropic 0.116.0 + httpx 0.28.1，而 requirements.txt 锁定 0.34.0 + 0.27.2。Docker 部署时才走锁定版本。两套环境行为可能不一致，建议：统一 SDK 版本（评估升级 requirements 至 0.116.x 并重新实测各协议），或本地改用 venv 按 requirements 安装。
2. **Docker 部署未重新验证**：本机无 docker 命令；修复后的 Dockerfile + docker-compose 需在目标环境重建镜像（`docker compose up -d --build backend`）并跑冒烟测试（scripts/smoke_test.sh）。
3. **服务无进程守护**：现网 uvicorn 以 nohup 方式运行在本机，Mac 重启/进程异常退出后不会自动拉起。建议接入 launchd 或改用 Docker 部署。

### 中优先级

4. **build.sh 设计缺陷**：构建完前端后会在前台直接启动后端，与已运行实例端口冲突，易误操作。建议拆分「构建」与「启动」两个动作，并让构建成为部署流程的强制步骤（runtime/static 是 gitignore 的，Docker 镜像依赖本地产物）。
5. **OpenAI 协议提供商未实测**：通义千问/智谱GLM/Kimi/豆包/Ollama 等预设仅按官方文档配置，未逐一实测（openai SDK 实际解析安装到 2.48.0，与 `>=1.40.0` 约束的兼容性未验证）。
6. **模型 max_tokens 上限未验证**：glm-4.5-air / glm-5.1 的网关侧最大输出未确认，当前统一 4096；若模型上限更低，长回复可能报错。
7. **长输出超时风险**：网关侧 API_TIMEOUT_MS=3000000（50 分钟），但 Docker gunicorn --timeout 600s、本机 uvicorn 无超时配置；深度分析长输出在 Docker 下可能被 600s 截断，建议评估对齐。
8. **管理员默认口令**：.env 中 ADMIN_USER=admin / ADMIN_PASS=admin123 为弱口令（.env 不入库），建议正式使用前修改。

### 低优先级

9. **前端主 bundle 1.24MB**：vite 构建提示 chunk 超 500KB，可做路由级代码分割优化首屏加载。
10. **urllib3 LibreSSL 告警**：启动日志有 NotOpenSSLWarning（macOS 自带 LibreSSL 2.8.3），不影响功能，换用系统 OpenSSL 或升级 Python 可消除。
11. **公司网关地址硬编码**：cai-gateway 预设将网关 URL 写死在代码中（平台要求请勿修改），若平台迁移地址需发版更新；如需灵活可后续改为数据库/环境变量注入。
