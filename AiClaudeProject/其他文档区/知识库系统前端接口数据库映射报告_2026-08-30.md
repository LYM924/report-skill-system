# 智能知识库系统 前端·接口·数据库 全面映射分析报告

> 生成日期：2026-08-30 ｜ 分析对象：`AiClaudeProject/projects/knowledge-base`（localhost:8000）
> 分析方法：前端/后端/数据层全量代码走读（约 1.9 万行）+ **线上 PostgreSQL 实测核对**（25 张表结构漂移与行数）+ 运行进程核对
> 与已有《知识库服务架构分析报告_2026-08-27.md》的关系：本报告在其高层架构之上，深入到「前端每个功能 → 接口 → SQL → 表字段」颗粒度，并纠正其一处关键误判（见 §1.5）

## 执行摘要（核心结论）

1. **系统定位**：智能知识库中台 = 产品业务知识管理 + 智能检索（BM25 全文 + FAISS 向量 + 关键词索引 + FAQ 缓存 + Claude AI 总结），React 前端 + Python 后端 + PostgreSQL，运行于 `0.0.0.0:8000`。
2. **双实现并存（关键事实）**：仓库内有两套后端——`src/server/search_server.py`（简易 ThreadingHTTPServer）与 `src/server/main.py`+`routes/`（FastAPI）。**当前实际运行的是 search_server.py**（`start.sh` 启动，进程已确认存活；8/29 的关键词修复提交也改在此文件）。FastAPI 版存在但从未运行，且与运行版行为严重分叉（写库 vs 写文件、关键词 HTTP 语义、search_logs/feedback 支持等），**不能作为现网行为依据**。
3. **前端 → 接口**：前端 21 个组件、45 个功能点、实际调用 **24 个端点**（关键词为 4 个 HTTP 方法）。这些端点在运行中的 search_server.py 上**全部存在**；但若切换为 FastAPI 版运行，将有 **7 项前端功能直接 404/405**（faq/import、document/update、document/upload、feedback、rag、search/related、关键词 POST/PUT/DELETE）。
4. **数据库**：PostgreSQL `knowledge_base`（`zcy1@localhost:5432`，.env 配置），25 张表 + 2 视图。SQLite `runtime/knowledge.db`（2.5MB，16 张表）仅作 PG 不可用时的回退与迁移源；`runtime/kb.db` 是 0 字节遗留空文件。
5. **表结构漂移（PG 实测）**：`faqs` 表在 PG 上**缺少 SQLite 遗留的 `related`/`tickets` 列** → `save_faq` 写库必失败、`get_all_faqs` 解析必 KeyError → **FAQ 主数据源实际退化为 `data/faq/*.md` 文件系统**。`document_departments` 表处于 `document_path`/`document_id` 双轨漂移（420 行全走 document_path，document_id 全 NULL），运行时写入 `ON CONFLICT (document_path, department_id)` 因 PG 无此唯一约束而**必失败**。
6. **关键词双表方案**：`keywords_v2`（1700 行）+ `keyword_mappings`（3407 行，其中 1674 行软删）已完全接管，旧 `keywords` 表已物理删除。软删除"复活"逻辑（`ON CONFLICT DO UPDATE SET is_deleted=FALSE`）+ 映射表无唯一约束 → 重复映射持续膨胀。
7. **检索引擎**：纯内存自研实现（jieba 分词 + 拼写纠错 + 同义词/拼音扩展 + 四路并行召回 + RRF 融合 + 本地规则答案生成）。schema_v3.sql 中为 PG 准备的 `tsvector` 全文索引、`unified_search` 视图、`dashboard_stats` 视图**在代码中零引用**，属未接线的备用设施。
8. **安全现状**：运行服务零鉴权（`KB_API_KEY` 未配置即全部放行）+ 三个路径穿越点（任意 UTF-8 文件可读、任意文件可删）→ 现网高危。
9. **前端质量**：api/index.js 26 个封装中 11 个是死代码；组件内 15 处裸 fetch 绕过封装；范围选择（scope）不传后端、分面筛选是假交互、4 个统计卡硬编码、部分编辑保存行为与 UI 语义不符（FAQ 编辑保存=新建）。
10. **数据写入真相**：运行版服务中真正写 PostgreSQL 的只有：search_counter（搜索计数）、feedback（反馈）、faqs（view_count 自增）、keywords_v2/keyword_mappings（关键词 CRUD）、document_departments（部门关联，PG 上失败）。其余内容数据（FAQ/文档/报表）的读写主体是**文件系统 + 内存索引**。

关键事实：

- **docker-compose.yml** 定义了 PG15+Redis+MinIO 容器化部署（`kb_user`/`kb_pass`），但本地实际以 `zcy1` 用户直连本机 PG，未用容器

### 1.5 双实现并存（重要，纠正 08-27 报告的误判）

《知识库服务架构分析报告_2026-08-27.md》称"FastAPI + uvicorn 为当前实际运行模式"，**实测不符**：

| 判据 | search_server.py（运行中） | main.py FastAPI（未运行） |
|---|---|---|
| 进程 | ✅ 存活（ps 确认，8/29 启动） | ❌ 无 uvicorn/gunicorn 进程 |
| start.sh | ✅ 指向它 | ❌ |
| 最近 5 个 git 提交改动的文件 | ✅（3e9b990 等直接改它） | 无 |
| 静态文件服务 | runtime/static | runtime/static（相同目录） |
| 关键词管理 | POST/PUT/DELETE /api/keywords → **写 PostgreSQL** | GET /api/keywords/add|delete → **只改内存，重启丢失** |

结论：**现网一切行为（含前端所调接口）以 search_server.py 为准**；FastAPI 版是半成品重构，两者分叉详见第九章。

## 二、前端功能 → 后端接口完整映射

### 2.1 前端应用结构

- **布局**：antd Layout 四区——TopNav（顶部 Tab：文档搜索/问答统计/知识管理/AI 问答）+ LeftSidebar（可折叠菜单）+ CenterContent（主面板）+ RightPanel（右侧看板，<768px 隐藏，可拖拽调宽）
- **路由**：无 react-router，纯 useState 状态切换（`topTab` + `selectedNav`），三个面板 React.lazy 懒加载
- **状态管理**：AppContext 形同虚设（`useAppContext` 全项目零消费），实际全靠 props + localStorage（`kb_dark_mode`、`kb_last_query`、`kb_search_history`、`kb_faq_drafts`）
- **鉴权**：前端无 token、无请求头、无登录逻辑（TopNav 用户下拉是纯静态 UI）
- **API 基建**：`apiFetch` 仅支持 GET（参数序列化为 query string），失败 console.error 后**返回 null**（调用方无法区分接口故障与空数据，统一走 fallback/mock）

## 三、后端接口逐个分析（运行中的 search_server.py）

### 3.1 服务器架构

| 项 | 说明 |
|---|---|
| 服务器 | `ThreadingHTTPServer`（ThreadingMixIn + HTTPServer），`daemon_threads=True`，每连接一线程（SSE 长连接可并发） |
| Handler | `SearchHandler(SimpleHTTPRequestHandler)`，构造时注入静态目录 `runtime/static` |
| 路由分发 | **纯 if/elif 链**（do_GET :288-1727）；`router.py` 正则分发器虽被 import 但全库无任何 `@router.route` 注册，`dispatch()` 恒返回 None |
| do_POST 分发 | /api/document/upload 独立实现；/api/feedback、/api/rag、/api/chat、/api/faq/import 直接委托 do_GET；/api/keywords → _handle_keyword_add；其余 404 |
| do_PUT / do_DELETE | 仅 /api/keywords（_handle_keyword_update / _handle_keyword_delete），其余 404 |
| 日志 | RotatingFileHandler → runtime/logs/search_server.log（5MB×5）；每请求一行访问日志；搜索行为追加 search_queries.log |

### 3.3 搜索类接口

#### GET /api/search（:306-443）— 全链路见第四章
- 参数：q（必填）、top=15、page=1、page_size=10（上限50）

#### GET /api/search/related（:1071-1080）

## 四、搜索全链路详解（运行版）

### 4.1 启动期数据装载（get_engine → SearchEngine.load_cache/load_all）

每次进程启动或缓存失效时，搜索引擎从 DB（优先）与文件系统（回退）装载以下内存结构：

| 内存结构 | 首选来源 SQL（PostgreSQL） | 回退来源 | 用途 |
|---|---|---|---|
| synonyms | `SELECT word, synonym FROM synonyms` | config/synonyms.json | 同义词双向扩展 |
| keyword_map | `SELECT ... FROM keyword_mappings km JOIN keywords_v2 kw ON km.keyword_id=kw.id LEFT JOIN modules m ON ... LEFT JOIN departments d ON ... WHERE kw.is_deleted=FALSE AND km.is_deleted=FALSE`（db_repo.py:220-244） | config/keyword_index.md | 关键词→模块路由、建议、FAQ 投票 |
| module_map | `modules m LEFT JOIN departments d LEFT JOIN products p LEFT JOIN product_lines pl` + 每模块 `SELECT level1,level2,level3 FROM module_menus WHERE module_id=?` + 模块关键词（`keywords_v2 JOIN keyword_mappings WHERE km.module_id=? AND 双表 is_deleted=FALSE`，db_repo.py:172-210） | data/modules/*.md | 模块匹配召回、意图检测 |
| menu_map | 由 module_map 派生 | — | 菜单命中 |
| product_module_map | config/module_map.json（⚠️冷启动 get_engine 路径不加载，见缺陷） | — | 上传文档自动模块匹配 |
| kb_docs | `SELECT path,title,content,dept,module,product,date,keywords,dept AS dept3 FROM documents WHERE is_deleted=FALSE`（content 截 5000 字符作样本） | data/knowledge/*.md | 文档列表、BM25 建索引源 |
| faq_docs | `SELECT * FROM faqs WHERE is_deleted=FALSE ORDER BY dept, sub_module, sort_num`（⚠️PG 上 _row_to_faq 因缺 related/tickets 列 KeyError → **实际回退文件系统** data/faq/*.md） | data/faq/*.md | FAQ 列表/缓存/相似 |
| report_docs | `SELECT path,title,content FROM reports WHERE is_deleted=FALSE` | data/reports/*.md | 报表检索/回退列表 |
| faq_cache | runtime/cache/faq_cache.json（⚠️冷启动不加载） | — | FAQ 缓存命中 |
| bm25 | runtime/cache/bm25_index.pkl（存在则加载；否则读各文档**全文** jieba 分词建倒排，k1=1.5, b=0.75） | — | 全文召回 |

### 4.2 查询处理流水线（SearchEngine.search，search_engine.py:919-1072）

```
用户查询 q
  │
  ├─ 1. QueryParser 高级语法解析（field:value、-排除、"短语"、AND）
  │     → filters / excludes / phrases / raw_query
  ├─ 2. jieba 分词（短语整体追加为 token；高级语法时对 raw_query 分词）
  ├─ 3. 拼写纠错 SpellCorrector（仅无高级语法时触发）
  │     词典=BM25 词频+keyword_map+module_map+menu_map+FAQ 标题
  │     COMMON_TYPOS 混淆表命中 confidence 0.95（如"这里报"→"浙里报"）
  │    否则编辑距离1-2 候选按 距离×长度比×首字×词频 评分，>0.3 采纳
  │    纠正词与原 token 合并去重（保留用户原意）
  ├─ 4. 意图检测 _detect_intent：硬编码 QUERY_INTENT_MAP（报销/接种/档案等词→模块集）
  ├─ 5. 查询扩展 _expand_tokens（:1074-1144）
  │     bigram 拼接 + 完整查询串(≤10字) + lcut_for_search 子词
  │     + synonyms 表双向同义词扩展 + 拼音扩展（ASCII token 匹配
  │       keyword/module/menu 拼音首字母/全拼 → 中文词）
  ├─ 6. 四路并行召回（ThreadPoolExecutor max_workers=4，:963-986）
  │    ┌─ _search_bm25_unified（:1248-1310）内存 BM25 倒排（KB+FAQ+报表同一索引）
  │    │    bm25.search(expanded, k=30)，source 按路径前缀分类：
  │    │    data/faq/→faq_knowledge、data/reports/→report_data、其他→knowledge_base
  │    ├─ _search_keywords（:1146-1178）内存 keyword_map 关键词路由
  │    │    评分：term==query 15；term≥3字且 in query 12；term in query 10；其他 8
  │    ├─ _search_modules（:1180-1246）模块名含 term 7；菜单名含 term 6
  │    └─ _search_vector（:1457-1475）FAISS 段落检索 k=10，score×10
  ├─ 7. RRF 融合 _rrf_fusion（:1312-1346）：score=Σ 1/(60+rank) ×100，key=path
  │    → 意图模块加权 +2 → deduplicate(source,module,path)
  │    → keyword_index 且无 path 的分数减半
  │    → 新鲜度加分（路径 8 位日期：90 天+3 / 180 天+2 / 365 天+1）
  │    → 高级语法过滤（filters/excludes 对结果字段子串匹配）
  │    → 多样性限制（同 dept 最多 5 条、同 module 最多 3 条）
  │    → _compute_facets（dept/module/source 计数 top15）
  └─ 8. 答案生成 _generate_answer（:1479-1566，本地规则，非 Claude）
       两阶段深度搜索（见 4.3）→ 返回 answer JSON
```

### 4.3 本地答案生成（_generate_answer 深度搜索）

1. 收集 keyword_index 命中的模块 + kb_path 目录为 priority_dirs
2. `_deep_search_kb`（:1793-1902）**两阶段**：
   - S1 文档级：bm25.search(terms, k=10) 粗筛；失败回退 `_collect_kb_paths_fallback`（priority_dirs + 结果路径 + module_map 部门/域 → `_domain_to_kb_dir` 硬编码目录映射）
   - S2 段落级：逐个读**文件全文**按 `###` 切段，四维评分：**关键词 40%**（高频通用词半权）+ **向量相似度 35%**（实时编码 query 与段[:512] 内积）+ **位置/标题 15%**（标题×3、父标题×1.5、FAQ 章节+2）+ **新鲜度 10%**（路径日期）；主题惩罚 ×0.5（`_check_topic_mismatch`）；阈值 0.15 取前 5 段；组同父章节
3. `_search_raw_docs`（:1941-1983）：data/raw-docs/*.md 按文件名倒序前 15 个标题加权匹配取 3 段
4. `_search_reports_deep`（:1985-2020）：results 中 report_data 的 path（≤3 个）切段匹配
5. `_infer_dept_from_kb`：路径第 2 段部门名分数累加 → `_select_best_module`（:2242-2306 主题评分）
6. `_build_summary`（:2356-2441）：问题类型判别、模块定位、最佳段落前 200 字、文档路径+行号、raw-doc 引用、段落图片提取
7. answer JSON：`{source:"qa_answer", question, module, dept, domain, dev_owner, module_owner, module_file, matched_keywords(≤8), matched_modules(≤5), kb_sections, raw_doc_sections, report_sections, images, score:20, summary}`

### 4.4 FAQ 缓存命中路径（/api/search 第 4 步）

`eng.check_faq_cache(query)`（search_engine.py:2445-2505）：向量余弦 **>0.85 直接命中**、>0.75 取最优；无向量时关键词交集兜底。命中 → `faq_hits+1`、save_counter → 直接返回 `from_cache` 结构（cached_answer 含 source/faq_cache/question/summary/module/matched_keywords/saved_at），**不执行常规搜索**。

### 4.5 Claude RAG 流式（build_rag_prompt :1703-1791）

- 结果排序：FAQ 优先 → kb/report → 其他，取 top5；每篇读文件全文（>8000 字符截断）组装 `### 来源 [i]: 标题\n路径\n部门\n内容`
- system prompt：中文回答、标注来源 [1][2]、末尾输出 `{"sources":[...]}` JSON
- 会话：`sid=uuid4().hex[:12]` → `SESSION_STORE[sid]={prompt,query,created}`（>600s 清理），持久化 runtime/sessions.json；前端通过 `/api/claude-stream?sid=` 消费 SSE
- **当前不可用**：`.env` 的 ANTHROPIC_AUTH_TOKEN 为空 → /api/search 不返回 claude_stream_url → 前端不渲染 AI 总结面板

### 4.6 索引缓存与重建

- 缓存文件：runtime/cache/{index_cache.json（文档/路径哈希/cache_version 校验）, bm25_index.pkl, vector_index.faiss, vector_meta.pkl, faq_cache.json}
- 增量更新：FAQ 保存/删除 → reload_faqs() 重建 BM25（**不重建向量**，缺陷）；文档上传 → add_to_index 增量 BM25
- 全量重建：/api/rebuild 或 /api/faq/import 结束 → 删 cache 目录 → SearchEngine().load_all() → save_cache()，**同步阻塞请求线程**（含向量 embedding，耗时最长）

### 6.3 表间映射关系总结（按数据流）

1. **关键词路由链**（搜索的核心映射）：用户查询词 →（扩展）→ `keywords_v2.keyword` →（`keyword_mappings.keyword_id`）→ `keyword_mappings.module_id` → `modules.id` → `modules.name`（召回模块）→ 模块部门 `modules.department_id` → `departments.id`；`keyword_mappings.kb_path` 直接指向知识库文档路径。即：**关键词 → 映射表 → 模块/部门 → 文档路径**。
2. **文档归属链**：`documents.path`（唯一标识）→（冗余列）dept/module/product/product_line 名称 → 各主表；多部门归属走 `document_departments`（线上以 document_path 关联）。
3. **FAQ 归属链**：`faqs.faq_code`（唯一）→ dept/module 文本 → departments/modules；标签走 `faqs.tags` 数组（GIN），**不**走 faq_tags 表。
4. **部门树链**：`departments.parent_id` 自关联 + `level` 分层；`departments.code`（FAQ 编码用）与 `departments.dir_name`（路径解析用）为两个独立派生字段（见 §7.6 dept_mapping 机制）。

### 8.3 软删除与"复活"机制（commit 3e9b990 修复脉络）

- **删除**：delete_mapping/delete_keyword 均软删（is_deleted=TRUE）；**硬删不可能成功**（keyword_mappings.keyword_id FK 无 ON DELETE CASCADE）
- **复活**：add_keyword 与 _save_keywords_to_db 用 `INSERT INTO keywords_v2 ... ON CONFLICT (keyword) DO UPDATE SET is_deleted=FALSE, updated_at=?` —— 再添加一个已软删的关键词 → 实体自动复活。修复前用 INSERT OR IGNORE，导致"添加成功但搜索不到"（实体仍 is_deleted=TRUE 被过滤）
- **外键崩溃修复**：module_id/dept_id 传 0 时转 NULL（PG 外键不允许 0）
- **残留副作用**：复活只复活实体不复活旧映射；映射表无 UNIQUE(keyword_id,module_id) → 每次复活+新映射累积重复行（线上 3407 映射/1700 词、1674 软删即证据）

**切换为 FastAPI 后将失效的功能（7 项）**：FAQ Excel 导入（#26）、文档元数据编辑（#30）、上传文档（#37）、结果反馈（#12）、AI 对话 RAG（#33）、相关搜索（#3）、关键词添加/更新/删除（#40-42）。此外 /api/faq/delete、/api/faq/suggest、/api/trends、/api/logs 因 Bug 会 500 或恒空。**结论：当前前端必须与 search_server.py 搭配运行。**

### 10.3 前端缺陷（详表见 §2.3）

重点：scope 不传后端、facets 假交互、FAQ 编辑保存=新建、统计卡硬编码、11 个死封装、15 处裸 fetch、fallback 字段不匹配。

### 10.4 建议修复优先级（供参考）

1. **P0 安全**：S1-S5（补鉴权、路径白名单校验、文件名 sanitize）
2. **P1 数据一致性**：B2/B3（统一 faqs 表结构与 document_departments 键设计——二选一：改表加列/加唯一约束，或改代码用 document_id）
3. **P1 功能**：B1（上传 NameError）、B5（关键词改名冲突）
4. **P2 一致性**：B4/B9/B12/B13、前端假交互与死代码清理
5. **P3 架构决策**：明确 search_server.py 与 FastAPI 双实现的主次（建议：以运行版为准回填 FastAPI 缺失端点并切换，或废弃 FastAPI 版避免误导）
